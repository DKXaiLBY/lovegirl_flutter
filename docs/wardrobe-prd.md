# 产品需求文档（PRD）：电子衣柜

版本：v1.0（2026-09-27 grilling 收敛拍板，平台 = LoveGirl 内嵌，见 §8；交互施工版与决策索引见 docs/wardrobe-interaction.md v1.0）
日期：2026-09-27
归属：情侣电子衣柜 · 新模块

---

## 1. 背景与目标

用户（情侣双方）希望把日常衣服和配饰数字化管理：拍照入库、打标签分类，并且把每天的穿搭记录下来（实拍或从衣柜组合），形成"我的穿搭档案"。

目标：
- 衣服"看得见、找得到"：按温度/类型/场合/风格快速筛出想穿的衣服
- 穿搭"留得下"：每天穿了什么有记录，形成日历式穿搭档案
- 搭配"有反馈"：搭配支持待确认/已通过的状态流转
- **情侣属性（已确认）**：衣柜是情侣向产品，TA 可以看我的衣柜、看我的穿搭

非目标（本期明确不做）：
- 虚拟试穿 / 数字人 / AI 换装（已评估为独立大方案，搁置）
- 电商比价、购物推荐

## 2. 用户与场景

- 用户：LoveGirl 的情侣双方（各自管理自己的衣柜；是否互相可见见 §7-Q1）
- 场景 A：买了新衣服 → 拍照入库 → 打标签
- 场景 B：早上纠结穿什么 → 按今天温度/场合筛选衣柜 → 选几件组合
- 场景 C：晚上记录今天实际穿的 → 拍照或选组合 → 存为当日穿搭
- 场景 D：翻日历回顾"上个月今天穿了什么"

## 3. 功能需求

### 3.1 衣柜单品管理（P0）

- **上传**：拍照或相册选图，单件单品一张主图；支持随后补传细节图（P1，最多 3 张）
- **自动抠图（M1，已拍板）**：上传后默认开启去背景（rembg U2Net），让衣柜网格视觉统一；可"保留原图"跳过、可重抠。**降级闸**：上线前服务器实测（2核/1.6G 内存紧），OOM/失败自动降级为仅压缩，服务端开关可远程关闭
- **标签编辑**：保存时必填「类型」，其余标签可选填、随时可改
- **编辑/删除**：删除=二次确认+提示影响搭配数；**软删**（行标记 deleted_at+清理图片文件），穿搭引用原样保留并渲染"已删除·{类型}"灰占位；不可经 UI 恢复
- **单品状态生命周期**：v1.0 仅 在柜 / 退役 两态（退役不显示在默认浏览中，筛选器可勾选查看）；在洗 / 收纳 M2 加入

### 3.2 标签体系（P0）

| 维度 | 单/多选 | 枚举（初稿，待用户确认删改） |
|---|---|---|
| 温度 | 单选 | 炎热(≥28°C) / 温暖(20-27°C) / 凉爽(10-19°C) / 寒冷(<10°C)，按整数℃取档无缝隙 |
| 类型（部位） | 单选 | 上装 / 裤装 / 裙装 / 外套 / 鞋子 / 包袋 / 配饰 / 连体装 |
| 场合 | 多选 | 日常 / 上班 / 约会 / 运动 / 正式 / 居家 / 旅行 |
| 风格 | 多选 | 休闲 / 甜美 / 简约 / 运动 / 复古 / 正式 / 潮酷 |
| 颜色（主色） | 单选 | 红/橙/黄/绿/蓝/紫/粉/黑白灰/棕/杂色 |

- 额外字段：品牌、价格（M1，§7.7 已确认）；购买渠道 v1.0 砍掉（品牌+备注可承载，如需 M2 再议）
- 存储：多选标签用 JSON 数组列（数据量小，不建标签表）

### 3.3 穿搭（P0）

两种记录方式：
- **A. 实拍记录**：当天穿搭拍照上传 → 生成一条穿搭记录（图片为主，可选关联衣柜单品）
- **B. 组合搭配**：从衣柜按类型选件（如 上装+裤装+鞋）→ 组合成套 → 标记穿着日期

状态流转（拍板：自我评价，无草稿态）：
```
实拍创建 → 已通过（可改回待确认）
组合创建 → 待确认 ⇄ 已通过
日期在未来 = 计划（叠加显示，非独立状态）
```
- "待确认/已通过" = 自我评价（自己标记"这套行不行"），无审核人
- 实拍是既成事实，保存即已通过；组合是计划，走 待确认 ⇄ 已通过
- 每条穿搭：穿着日期（必填）、备注（选填，心情并入备注）、来源（实拍/组合）
- 一天可以有多条（早班装/晚约会装）

### 3.4 浏览与检索（P0）

- **衣柜网格视图**：按"类型"分 8 节展示，节内添加时间倒序；"按添加时间平铺"切换视图 M2 再议
- **筛选器**：温度 / 类型 / 场合 / 风格 / 颜色 / 状态（v1.0 仅在柜/退役），多条件叠加；衣橱页常驻「今天 N°C·档位」胶囊一键预填温度筛选（天气与首页同源，取不到则隐藏）
- **穿搭视图**：按日期倒序列表 + 月历视图（P1，日期上有穿搭的点标记）
- **统计（P2）**：总数、各分类数量、穿着次数 Top、买来没穿过（闲置提醒）

### 3.5 情侣维度（P1，LoveGirl 差异化）

- TA 可以浏览我的衣柜（只读）
- TA 可见我的全部穿搭状态（含待确认——自我评价非隐私）
- TA 发起搭配 → M2 后期（"TA 搭的算谁的待确认"归属未清，v1.0 先跑通单人闭环）
- 情侣装标记（P2）

## 4. 数据模型（草案）

```
wardrobe_items
  id, user_id, image_url, thumbnail_url, extra_images(JSON),
  category, temperature, occasions(JSON), styles(JSON), color,
  brand, price, status(在柜/退役，在洗/收纳 M2), favorite(预留,无UI),
  wear_count, deleted_at(软删,空=正常), created_at, updated_at

wardrobe_outfits
  id, user_id, worn_date, source(实拍/组合),
  photo_url(实拍时), item_ids(JSON,实拍关联与组合均存),
  status(待确认/已通过),
  note, created_at, updated_at
```

- 图片：复用现有 multer 上传模式，服务端生成缩略图（现有 photos 模式）；删除单品时同步清理其图片文件
- wear_count 冗余列随状态迁移**条件更新**（WHERE status=旧值，保证双端重复提交幂等）：进入已通过 +1；离开已通过 -1（改回待确认/删除已通过记录/编辑移出单品按差量）；实拍关联单品同口径
- 接口：`/api/wardrobe/items`（CRUD）+ `/api/wardrobe/outfits`（CRUD+状态流转）

## 5. 非功能需求

- 图片上传前 App 端压缩（长边 1600px），服务端出缩略图——2核/1.6G 内存服务器的磁盘与流量保护
- 单品图与穿搭图归属 user_id 隔离；TA 可见性按 §7-Q1 的决定实现
- 老设备兼容沿用现有图片组件

## 6. 里程碑建议

- **M1（P0）**：单品上传/标签/编辑/分类浏览 + 组合搭配（含计划穿搭）/实拍记录/状态流转 + 基础筛选+「今天」胶囊 + 抠图（带降级闸）+ 空态插画与入口图标素材
- **M2（P1）**：细节多图、在洗/收纳状态、穿搭月历、TA 视角（含发起搭配后期）、平铺视图（再议）
- **M3（P2）**：统计与闲置提醒、天气联动、情侣装

## 7. 需求问答结论（2026-09-27 已确认）

1. **情侣衣柜**：TA 可以看我的衣柜和穿搭（只读=v1.0；发起搭配=M2 后期，见第 9 条）
2. **待确认/已通过 = 自我评价**：不是 TA 审核，是我自己标记"这套行不行"
3. **温度四档**：≥28 炎热 / 20-27 温暖 / 10-19 凉爽 / <10 寒冷 ✓
4. **类型枚举**：按 §3.2 八类执行 ✓
5. **要自动抠图** ✓（上传后去背景，可选开关，rembg 方案）
6. **入口**：生活 tab 内（生活页头卡第五入口/子页签，施工时按实际空间定）✓
7. **记录品牌和价格** ✓
8. 场合/风格枚举按 §3.2 建议值执行 ✓
9. **v1.0 收敛拍板（2026-09-27 grilling）**：平台=内嵌；实拍保存即已通过；计划穿搭保留；抠图默认开+降级闸（M1）；「今天」胶囊 M1；TA 全状态可见；单品状态 v1.0 两态（在柜/退役）；TA 发起搭配 M2 后期。完整决策索引见交互文档 §7

## 8. 平台归属（已定 2026-09-27）

**LoveGirl 内嵌模块**，入口=生活 tab 子页（生活页头卡第五入口/子页签，施工时按实际空间定）。交互设计以 `docs/wardrobe-interaction.md` **v1.0 施工版**为准（grilling 两轮收敛，决策索引见其 §7）。独立 App / 微信小程序为后续产品化路径：微信【深度合成】类目个人主体不可申请，但抠图=图像分割不构成深度合成，功能命名"一键去背景"可过审；竞品（搭搭/Acloset）均为独立 App，小程序形态存在差异化机会。
