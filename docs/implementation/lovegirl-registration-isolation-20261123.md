# LoveGirl 邀请注册与账号隔离

## 已确认的使用方式

正式服保留 `testgirl` 和 `testboy` 的登录、账号和历史记录。用户本人生成注册邀请码，对方设置自己的用户名、昵称和密码。注册完成后进入她自己的空间。双方之后通过现有「伴侣绑定」流程确认关系。已有账号可以继续使用原凭据登录。

## 现状和方案选择

正式服已有注册入口，`/api/auth/register` 按角色各允许一个普通账号。两个普通角色都由历史测试账号占用。线上待办、账本、课程、饮食、联系方式等路径还有按角色选人或检查隐私的查询，`/uploads` 是公共静态路由。上线新的账号之前需要补齐这两类边界。

| 方案 | 取舍 |
|---|---|
| 在现有后端按账号和伴侣关系授权 | 复用数据库、版本更新、绑定界面和已有的按成员授权逻辑。每条旧查询及私有媒体需要核对。推荐。 |
| 给每组伴侣单独部署数据库、文件存储和 App 接入 | 部署层可以独立划分数据。账号登录、现有数据归属、更新和跨工作区维护都需要增加机制。适合以后有独立托管需求时评估。 |

## 注册与绑定

- 管理员在「我们」生成用于注册的新邀请码。邀请码只用于创建一个账号，校验有效期，允许重新生成并作废上一枚。服务器保存邀请码的散列。注册、登录日志和下载包不含邀请码或密码。
- 注册输入沿用现有表单并新增邀请码字段。校验字段、邀请码、用户名唯一性，创建账号和默认设置，在同一个事务里消耗邀请码。处理两个设备同时提交、已使用、已过期、用户名重复、创建中途失败和当前账号错误等情况。
- 注册成功自动登录。伴侣绑定沿用原入口和独立的绑定邀请码，由新账号确认。有效关系基于两人的账号 ID。处理同一账号并行绑定和解绑后换人，防止历史关系因库中的位置唯一键重新激活。按同一顺序锁两个账号，查询双方是否已绑定，在事务内写关系和消耗绑定邀请码。

## 资料授权

- 未绑定时个人页面及媒体只开放给所有者。已绑定时只给当前关系的两名成员共享允许共享的条目，经期、私有草稿、隐私设置和其他个人数据继续按本人权限处理。解绑后立刻重算访问权限。
- 服务端用真实账号 ID 与有效伴侣关系查找成员。角色继续表达页面与功能选项。逐条复核现有主要模块的列表、详情、编辑、删除、聚合、消息、导出和通知。重点核验按角色选人的资料、待办、课程、账本、饮食、天气、旧聊天，以及首页合照/回忆、相册、作品、地图、衣橱等资源入口。
- 私有上传文件的下载与缩略图使用服务器校验后的资源入口。按文件实际归属和当前访问者权限确认可读性，保护照片、附件及个人导出。覆盖旧文件引用、App 缓存切换账号、解绑后的旧地址和公开 APK 更新通道。已有数据保留原所有者。首次启用前为旧照片和引用核对实际归属。

## 上线门槛

1. 保留客户端安装包、源码、线上受影响路由、关系与邀请表的回滚点。先在隔离库升级和回滚一次，以现有线上文件为修改基线。
2. 用正常注册和登录流程开出两组伴侣与一个未绑定账号。验证两个旧测试号仍可登录。对共享、私有、未绑定、解绑、重新绑定分别核对列表、已知记录详情和媒体地址。两组账号互不可读写。
3. 验证邀请码过期、重复、并发提交和网络失败，失败时表单仍保留输入，失败事务不产生半个账号，也不会消耗可再次使用的邀请码。
4. 用荣耀走「生成注册邀请 → 注册 → 自动登录 → 单独确认绑定」，再走旧账号登录与应用内升级。只在账号与媒体访问验证通过后启用正式注册。正式服用只读检查或已授权的受控数据验收，保留旧账号及真实记录。
