# 电子厨房：执行契约与检查记录

承接已授权的`lovegirl-clear-ui-roadmap-20261031.md`第6节。本文把既定的“菜单／这一餐／开饭记录”落实为可实现的约定，不表示整个厨房已完成或已发布。正式版本仍为4.4.2+187；当前仅自有隔离QA服务使用新路由。

## 页面与真实数据

- 菜单按`08-kitchen-menu.png`组织：冷白淡蓝背景、玻璃返回/管理按钮、三段导航、搜索、横向分类、两列大照片、菜名与短推荐语、48逻辑像素数量操作、口味备注、底部确认托盘。没有照片时使用中性缺图态，不能填样例菜；价格不作为主层级，也不代表实际付款。
- 首屏“今晚由谁掌勺”选择当前本人或已绑定伴侣，显示该主厨的菜单；切换主厨且已有选菜时先确认清空，不混合不同主厨的菜。未绑定可管理自己的菜单，双人点餐再引导绑定。
- 标题右侧管理进入自己的菜单，能添加、编辑和下架；菜品详情保留完整照片和可选食材/做法，缺资料明确提示。食材和做法不是首次录入的必填项。
- “这一餐”集中待确认和已接下的餐次，展示菜品快照、数量、口味、时间及主厨。点餐人与主厨可提出修改；修改后重新确认，明确告知，不能在对方已开饭之后覆盖。
- “开饭记录”展示已完成餐次；能回看当餐快照与对应美食手账。美食手账仍是独立的餐桌回忆，不能被厨房菜单替代。

## 状态与失败规则

| 动作 | 条件与结果 |
|---|---|
| 确认这一餐 | 主厨属于当前绑定双方；所选菜属于主厨的有效菜单。保存菜名/数量等快照，不依赖未来菜单是否下架 |
| 接下这一餐 | 仅指定主厨操作，`placed → accepted` |
| 撤销接单 | 仅指定主厨，`accepted → placed`；清空接单时间，保留原选菜/备注，通知对方重新商量 |
| 修改菜/口味/安排 | 仅餐次双方，未完成/取消；携带revision，过期返回409并保留表单。修改已接餐次要回到待确认 |
| 开饭 | 仅主厨，`accepted → done`；照片可选。完成后不能撤销回待接，重复完成返回原结果，不重复通知或写回忆 |
| 取消 | 点餐人可取消`placed/accepted`；保留历史和原因，不删除菜品或原有手账 |

请求进行中禁用当前餐次动作，其他餐次仍可浏览。失败不关闭确认/编辑表单，不清掉照片、选菜或文字；照片已上传但保存失败时复用该上传结果重试。刷新与状态冲突不得把他人的新内容当成本次保存成功。

## 后续持久化约定（尚未施工）

1. 菜品增量增加可空`ingredients`和`recipe`，原菜品无需迁移内容。
2. 餐次增量增加可空用餐日期/时段、`revision`和请求标识。新客户端对同次提交保留请求标识，服务端唯一约束配合请求内容校验防重复；输入改变后生成新的提交标识。旧客户端不带新字段仍能完成原流程。
3. 餐次主厨沿用`cook_id`；允许本人或当前伴侣，不能提交任意第三人。菜单与购物车、未完成请求均按登录账号隔离，账号变化后丢弃旧响应。
4. 新完成的餐次与`cooking_logs`建立唯一订单关联，在同一事务写入一次餐桌回忆；复用既有品尝/照片/做法/时光轴能力。既有已完成订单不批量补造回忆；旧照片与原美食手账不改。
5. 行程、原衣物和其他生活工具不为厨房改造迁移或清空。所有schema修改先在自有QA库验证，正式部署前再次核对live并保留兼容回退路径。

## 账号隔离补修

- 根厨房Provider现与Auth账号关联，登录/退出/切换后同步清空菜单、伴侣、餐次、购物车、红点、错误和忙碌状态；没有删除账号在服务器的菜品、餐次或其他历史内容。
- 菜单、餐次、汇总分别校验当前会话与最新请求；过期响应不会覆盖新账号或较新的刷新。菜单与餐次错误分开保留，避免另一个成功请求把失败状态抹掉。
- 旧账号的下单/菜品/状态写入返回后，不清新购物车、不启动新账号刷新、不释放新账号正在进行的提交；切换期间提示核对账号。已被服务端接受的原请求仍属于请求认证账号，本改动不声称撤销了服务器已经提交的操作。
- 6项回归覆盖切换清空、延迟菜单/餐次、同账号乱序刷新、旧下单与新购物车/忙碌状态、旧菜品写入和销毁后返回。全套217项通过，analyze0，日志`kitchen-account-full-tests.log`与`kitchen-account-final-analyze.log`。静态退役入口/调用/奖励文案审计继续为0命中。
