# LoveGirl 清透界面与生活功能改造规划（审阅稿）

日期：2026-10-31。当前交付是规划与参考图归档，尚未开始本轮产品代码、数据库或服务器修改，也未创建新的执行目标。本稿接续已发布的 4.4.2+187，不能将上一轮三模块局部 UI 验收描述为本轮全 App 改造已完成。

## 1. 已确认的方向与范围

- 核心用途：记录两个人的日常与回忆，保留真实街道地图及生活工具。
- 底部继续为：今天、回忆、旅行、生活、我们。改造主页面及其主要二级页面的内容组织和交互；账户设置、账目等适合阅读的信息仍可使用列表。
- 视觉以用户认可的清透参考图为基准：冷白与淡蓝的中性外围、真实照片为主要内容、克制的玻璃控件、光面相纸和哑光票根。生活照片自身的颜色不等于将外围主题改暖。
- 确认精简：每日一问、慢信、爱心豆、签到、成就、愿望兑换券。精简涉及入口、调用和奖励事件；不能仅隐藏菜单后声称整个功能已移除。
- 厨房按私人电子菜单与每餐协作设计；美食手账保留为餐桌回忆。两者可以关联，职责与入口分开。
- 优先新增：旅行准备，关联已有行程、衣橱搭配和行李清单。护肤用品管理等只是备选，本轮不默认加入。
- 备用机无法登录微信。竞品依据短视频可访问说明、字幕、公开演示与必要的自主设计；不得声称已在真机完整测试“独家御膳房”。

规划时源码基线：`f90b9dd93cb0eca276bfe234d58ed236f221c7d5`。实际开工与每次发布前重新核对工作区、远端和线上状态。

## 3. 推进方式与取舍

| 方式 | 取舍 |
|---|---|
| 一次性混合全局 UI、厨房重建和旅行准备 | 耦合大，视觉偏差和数据问题难以定位，回滚也困难 |
| 逐页换外观，继续增加入口 | 容易出现首页好看而二级页仍是旧样式，使用流程缺口仍在 |
| 先验证材质与页面，再分阶段完成完整流程（推荐） | 先用真机证明参考图能够落地；各阶段有清楚的完成边界与独立回滚点 |

## 4. 阶段与完成条件

| 阶段 | 主要交付 | 达到什么标准才进入下一阶段 |
|---|---|---|
| P0 定稿与基线 | 页面清单、参考图对应、关键状态、依赖清单、源码和发布包回滚点 | 主页面与重要操作均有去向；拟定规则与未知项写清；备份可读且散列正确 |
| P1 真实页面验证 | 完整生活页，以及真实地图上的玻璃浮层验证 | 使用受控素材与图稿对照；布局、玻璃和图片比例达到要求；荣耀操作跟手，SDK 限制有实际证据与解决方案 |
| P2 主页面及主要二级 UI | 五个主导航、统一控件和主要二级页面；移除六项功能的前台入口 | 入口可达、返回正确、真实内容与空态均完整；每页视觉逐项核对；不能以仅改共享颜色宣布完成 |
| P3 精简依赖与厨房闭环 | 停止被取消的奖励事件；完成电子厨房日常流程和已发现问题修补 | 不再产生相关奖励；旧数据保留且旧版兼容方案明确；双会话/真机实际验证厨房成功、失败和冲突路径 |
| P4 旅行准备 | 行程关联、每日搭配、个人行李、共同物品 | 关联与持久化真实可用；私密与共同内容权限明确；改名、下架、解绑及删除关联有正确结果 |
| P5 总体验收与发布收尾 | 全链路复核、实际截图、功能检查、正式安装包与交付说明 | 视觉和功能分别通过；数据保护检查通过；更新提示、公网包、安装包与版本说明一致 |

P2、P3、P4可形成独立版本，每个发布单元必须本身可用并通过必要验证；部分阶段交付不等于整个改造目标完成。视觉原型或占位按钮不作为正式功能发布。

## 5. 页面应当如何组织

| 页面 | 主体与操作 |
|---|---|
| 今天 | 紧凑日期与双人信息；真实生活照片；少量当天事项和临近纪念日。有内容才展示对应模块，不填假数据 |
| 回忆 | 大张相纸浏览、票根集合、按月内容；进入真实作品、原照片、编辑与导出。既有作品能力不因首页重排丢失 |
| 旅行 | 地图占主体；选点出现照片浮卡；行程可展开、按日组织。地点、卡片、路线选择同步，控件不挡当前地点 |
| 生活 | 真实待办/账本摘要；厨房与衣橱图片预览；临近出行时显示准备入口。私密经期内容只在本人可见范围展示 |
| 我们 | 双人关系、重要日子、绑定与设置。取消的积分与兑换入口退出，新页面不靠空统计补面积 |
| 待办/记账/课程 | 可直接操作的轻清单、月度摘要与账目、周课表；表单、键盘和返回路径一并设计 |
| 衣橱/经期 | 衣物与搭配陈列；月历和当日记录。经期“安全期”文案需纠正，不能暗示避孕保证；不擅自改变预测算法 |

主页面素材来源、照片裁切、标题长度、缺图与少量数据的布局必须同时确定。真实内容替换设计图示例之后，仍应保持同样的视觉层级。

## 6. 厨房：基于已核实问题收口

此前只读核对中，线上厨房与本地副本源码按换行归一后相同；线上 `kitchen.js` SHA256 为 `ab84418757f621dfb5befdd7232108d9442520e3d0bd05b7b5b5a610e296fa07`。这是该次观察时点，施工前必须再核对 live。

- 已有菜单、购物车、下单、接单、完成与历史记录接口；不能描述成从零开始。
- 未绑定时前端整页阻止进入个人菜单；拟改为个人可先建菜，双人点菜再检查关系。
- 撤销接单发送 `placed`，线上状态接口不支持；相同源码的隔离调用已确认返回400，未写入生产数据。
- 下单、菜品保存失败仍关闭弹窗；需保留输入并可重试。下单还需忙碌状态与后台防重复机制。
- 当前菜品缺少独立的完整做法/食材资料；基础录入保持简短，食材和做法为可选补充。
- 当前完成订单要求成品照并发豆；美食手账也存在奖励与成就触发。精简时一起核对依赖，避免破坏完成和保存流程。
- 厨房完成记录与美食手账尚非完整双向流程；手账已有挂菜单能力，应利用现有关系，避免重复造记录。

拟采用的主结构为“菜单／这一餐／开饭记录”。基本流程：选菜 → 数量与口味、开饭安排 → 对方确认或协商调整 → 开饭 → 可选补照片并保存餐桌回忆。双方按每餐轮换掌勺；照片不应成为结束一餐的强制门槛。采购清单、周菜单、随机候选菜不挤进第一阶段。

## 7. 旅行准备：最小完整范围

- 从已有行程进入准备页，也可从生活页选择行程；不再独立创建一套旅行数据。
- 每日搭配引用已有衣物/穿搭；缺少衣物时提供清楚的选择或添加路径，不能用示例服饰冒充用户衣橱。
- 个人行李与共同物品区分；支持分类、增删、勾选和持久化，共同物品可标记携带人。
- “已装好”进度由真实清单计算，不引入积分和签到。
- 拟采用：删除准备关联不删除原衣物、原搭配、地点和作品；取消行程时归档准备内容；解绑保留个人清单并收回共同访问。具体共享及数据约定须在本阶段设计中确定后实现。
- 自动天气搭配、AI 选衣、商城、护肤模块、多人家庭权限扩展不纳入首轮。

## 8. 视觉与交互验收

| 维度 | 证据与标准 |
|---|---|
| 布局 | 参考图与实际页面使用同一组受控素材并排核对，记录主图/卡片占比、边距、字号、层级和主要操作位置 |
| 玻璃 | 背景实际透出中心，边缘高光与暗缘存在；在照片与真实地图背景上检查，不能仅以卡片后方光影替代 |
| 相纸与票根 | 薄边、接触阴影、光面照片与哑光纸票分别成立，文字和日期在正常浏览下清楚 |
| 触控与反馈 | 新自绘交互目标至少48逻辑像素；按压、选中、提交与失败反馈明确；遵循系统及 App 关闭动态偏好 |
| 适配 | 荣耀360逻辑宽、原系统字号及较大字号、亮暗模式、键盘、底部系统区域均检查；空/少/多数据及长文本可用 |
| 性能 | 真实地图与浮层同时操作检查；避免重复创建原生地图和常驻装饰动画；性能结论必须来自实际测量范围 |
| 数据 | 页面引用真实记录；加载、空态、失败和未绑定分别处理；私密数据不进入共享预览 |

功能测试通过、安装包构建或发布成功均不能代替视觉验收。不达参考图约定的页面记录为未完成，先解决具体差距。实际 SDK 底图几何与生图可能不同，定稿时明确可控的配色、布局与控件目标；不可达项先出真机证据和替代设计，不擅自缩水。

## 9. 备份、兼容与发布

- 正式施工前备份当前源码、正式 APK 和发布元数据；涉及后端时先拉 live 文件与 schema，记录行数/散列并验证备份可恢复。
- 历史照片、作品、地点、衣物、账目和私密记录不为界面重排而迁移或清空。被取消功能的数据先备份保留，本轮不默认删除表或字段。
- 分别追踪“前台入口退出”和“后台奖励/调用退出”，核查厨房、手账等依赖以及仍在使用的旧客户端。
- 各阶段独立提交、可回滚；兼容性涉及后端或数据时，不仅保留旧 APK，还应给出相应服务端回退或向前修复办法。
- 正式构建不带测试自动登录参数；发布凭据按既有规程仅在服务器容器内使用，不进入文档、输出或文件。
- 沿用既有发布授权：验证通过后发布、核对中文说明和版本元数据、旧版升级/新版不重复提示、公网完整 APK 与构建产物散列。
- 使用荣耀备用机验收；发现他人同时操作时暂停手机控制，可继续独立工作。微信登录不是本轮前置条件。
