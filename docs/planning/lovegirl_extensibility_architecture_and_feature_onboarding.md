# LoveGirl 可扩展架构与新功能接入规范

更新时间：2026-07-17
适用阶段：方案确认阶段（当前不写业务代码）

## 1. 这份文档解决什么问题

这份文档回答的是：

- 后续如果还想继续加功能，应该加到哪里
- 哪些代码可以复用，哪些代码不能乱塞
- 新功能接入时，前端、后端、数据库、联动、首页摘要各自怎么落位
- 如何避免 LoveGirl 再次回到“功能越来越多，但结构越来越散”的状态

它不是业务功能清单，而是“以后所有新增功能都要遵守的接入规则”。

## 2. 可扩展性的定义

对 LoveGirl 来说，“可扩展”不是抽象概念，而是下面这些具体结果：

- 新增一个功能时，不需要去 10 个无关文件里补洞
- 新增一个模块时，能明确说出它属于哪个 domain
- 新增一个联动时，能明确说出谁写数据、谁读摘要、谁负责展示
- 删除一个旧功能时，不会牵连核心主链路
- UI 能复用设计系统，不需要每页重新拼一套风格
- 后端能补接口，而不是继续靠前端硬猜字段

只要做不到这些，就不能算“方便以后继续加功能”。

## 3. 架构总原则

后续所有实现都遵守下面 6 条：

1. 先定 domain，再写页面  
   任何新功能都必须先归属到明确业务域，不能先写页面再找地方塞。

2. UI、状态、服务、模型分层  
   页面只负责展示和交互；状态层负责读写状态；服务层负责 API；模型层负责结构化数据。

3. 首页只读摘要，不承担重业务  
   首页是聚合层，不直接承载复杂写入逻辑。

4. 联动必须有来源和归属  
   任何自动生成、自动同步、自动沉淀，都要明确是哪个模块触发、写到哪里、被谁展示。

5. 通用能力上提，业务判断下沉  
   样式、空状态、按钮、卡片、网络层放公共层；投喂、旅行、记账等业务判断放回各自域。

6. 新增功能必须能被删除  
   如果一个功能加进去之后，未来无法干净删除，说明当前接入方式已经有结构问题。

## 5. Domain 划分规则

### 5.1 Home

负责：

- 恋爱天数
- 天气与体感温度
- 今日照顾卡
- 回忆票根
- 旅行票根
- 生活摘要
- 快捷入口

规则：

- 只读各域摘要
- 不直接负责复杂新增、编辑、删除业务

### 5.2 Feeding

负责：

- 店铺
- 商品
- 下单
- 订单追踪
- 履约状态
- 平台信息
- 爱心豆抵扣展示

规则：

- 订单状态是本域主数据
- 对记账、时光轴的同步只通过明确联动逻辑触发

### 5.3 Travel

负责：

- 旅行预览页
- 真地图模式
- 地点
- 路线
- 花费
- 打卡
- 成就
- 旅行票根

规则：

- 地图显示、路线、地点详情全部归 Travel
- 首页只读 Travel 摘要，不直接控制地图逻辑

### 5.4 Life

负责：

- 待办
- 愿望清单
- 记账
- 课程表

规则：

- 这 4 个模块属于同域，但保持子能力独立
- 待办和愿望共享结构能力，不合成同一个心智模型

### 5.5 Memory

负责：

- 相册
- 照片
- 纪念日
- 倒数日
- 时光轴
- 随机回忆
- 月度报告

规则：

- 所有“回忆沉淀层”能力都归这里
- 旅行打卡、投喂里程碑等内容只能作为来源写入，不在外域各自复制一份时间线展示

### 5.6 Relationship

负责：

- 私密聊天
- 伴侣绑定
- 关系资料
- 权限和角色区分

### 5.7 Health

负责：

- 经期管理
- 经期对投喂推荐的影响

规则：

- 只暴露可联动的推荐状态
- 不把敏感数据直接散给其他域

## 6. 新功能接入流程

以后每新增一个功能，都按下面 8 步走：

1. 先判断它属于哪个 domain
2. 再判断它是新模块、子能力，还是现有模块扩展
3. 明确它的核心数据实体是什么
4. 明确它需要哪些前端页面和 Provider
5. 明确它需要哪些后端路由和表
6. 明确它是否需要首页摘要
7. 明确它是否会联动爱心豆、记账、时光轴
8. 明确它的删除路径是否清晰

如果这 8 步说不清，就不应该直接动代码。

## 7. 新功能接入模板

后面只要想新增功能，都应该先写成下面这个最小模板：

### 功能名称

一句话说明这个功能解决什么问题。

### 所属 domain

它归属于：

- Home / Feeding / Travel / Life / Memory / Relationship / Health

### 主数据

至少回答：

- 核心实体是什么
- 谁创建
- 谁修改
- 谁查看

### 前端落点

- 需要新增或修改哪些 `screens / providers / services / widgets / models`

### 后端落点

- 需要新增或修改哪些 `routes / services / tables / migrations`

### 联动关系

- 是否写首页摘要
- 是否写记账
- 是否写时光轴
- 是否参与爱心豆

### 验收方式

- 用户怎么操作
- 看到什么算成功
- 什么情况算失败

## 8. 通用能力怎么复用

### 8.1 必须复用的公共能力

以下能力后续必须优先复用，而不是每个模块自己重造：

- 主题色板
- 文字层级
- 卡片样式
- 按钮样式
- 底部抽屉
- 空状态
- 加载态
- 错误态
- API 基础请求封装
- 通用上传能力
- 通知能力

### 8.2 不应该做成全局黑洞的能力

以下东西不能变成“什么都往里塞”的大杂烩：

- `ApiService`
- `main.dart`
- `HomeProvider`
- 单个超大页面文件

这些位置现在已经有“过度集中”的历史痕迹，后续要收口，而不是继续叠加。

## 9. 联动设计规则

联动是这次 LoveGirl 重构的灵魂，但也最容易失控，所以必须定规则。

### 9.1 联动只允许 3 种类型

1. 摘要联动  
   例如课程摘要、待办摘要、纪念日提醒显示到首页。

2. 记账联动  
   例如投喂完成自动记账、旅行花费同步记账。

3. 沉淀联动  
   例如旅行打卡生成时光轴、投喂里程碑生成时光轴。

### 9.2 联动必须写清 4 个问题

- 谁触发
- 写到哪里
- 谁读取
- UI 怎么体现

凡是答不出这 4 个问题的联动，先不做。

### 9.3 联动不允许反客为主

联动是增强体验，不是篡改原业务。

例如：

- 旅行记账是为了减少重复录入，不是让 Travel 取代 Finance
- 首页摘要是为了好看懂，不是让首页接管各域业务逻辑

## 10. 数据与接口扩展规则

### 10.1 数据表原则

- 每个 domain 的主表归本域维护
- 联动表或流水表单独建，不把联动硬塞进主表
- 涉及状态流转的能力，优先保留状态历史或流水痕迹

### 10.2 迁移原则

- 所有结构改动都通过迁移脚本进入
- 不允许只改代码不补迁移说明
- 可删除字段和历史兼容字段必须标明淘汰计划

### 10.3 接口原则

- 前端不直接依赖“猜测字段”
- 后端响应结构要稳定
- 模块接口命名按 domain 收口
- 外部第三方能力尽量通过后端代理，不直接暴露敏感 Key

## 11. UI 扩展规则

以后新页面必须满足下面这些要求：

- 先判断它属于“票根 / 卡片 / 抽屉 / 列表 / 表单 / 详情”哪一类
- 优先复用现有设计 token，不新造风格
- 不使用和当前母版冲突的办公风图标、颜色和排版
- 中文文案优先自然表达，不出现机器翻译感
- 空状态不是只有一句“暂无数据”，要说明下一步能做什么

## 12. 删除与替换规则

这轮已经确认会删掉一部分模块，所以后续所有删除都要按同一标准：

- 删入口
- 删页面
- 删 Provider / Service 方法
- 删 API 调用
- 删后端路由
- 删无用表或明确废弃状态
- 删联动残留

只删前端按钮，不算删除完成。

## 13. 后续实现阶段的硬性门槛

从方案切换到实现后，每个新增功能或重构任务，至少都要满足下面这些检查：

- 能说清 domain 归属
- 能说清数据落点
- 能说清是否联动首页、记账、时光轴、爱心豆
- 能说清删除路径
- 能说清验收方式

否则不进入开发。

## 14. 这份规范如何使用

后面进入实现阶段时，建议顺序是：

1. 先看根目标入口文档
2. 再看 `docs/planning/README.md`
3. 再看总方案、模块审计、实施路线
4. 如果开始做具体模块或准备新增能力，再看这份文档

它的职责很简单：

- 不替代产品方案
- 不替代接口文档
- 只负责保证结构可持续增长

## 15. 结论

LoveGirl 这次不是只做“把几个页面改好看”，而是要把它变成一套以后还能继续长、继续加、继续联动、继续发布的情侣 App。

所以这份规范最终要守住的，不是形式上的目录整齐，而是三个结果：

- 新功能知道加在哪
- 旧功能知道怎么删
- 核心体验不会因为继续扩展而再次变乱
