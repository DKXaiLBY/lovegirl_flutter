# LoveGirl 当前状态审计（2026-07-17）

更新时间：2026-07-17
适用阶段：方案确认阶段（当前不写业务代码）

## 1. 文档目的

这份文档记录的是“当前仓库真实长什么样”，不是目标状态。

它的作用是：

- 固定本轮重构的起点证据
- 让后续实施时不用再重复摸底
- 让“为什么要重构”有具体结构依据

## 2. 审计范围

本次审计基于当前仓库的可见文件与已读取关键文件，重点覆盖：

- Flutter 前端目录结构
- Provider 数量与页面数量关系
- 主入口结构
- API 服务集中度
- 后端 `server_fixes` 现状
- 已有数据库迁移方向

结论：

- 后续继续叠加功能会越来越乱

### 3.2 Provider 结构规模

当前 `lib/providers` 下只有 **4 个 Provider 文件**：

- `auth_provider.dart`
- `home_provider.dart`
- `theme_provider.dart`
- `travel_provider.dart`

结论：

- 页面层已经远大于状态管理层
- 当前 Provider 颗粒度明显偏粗
- 后续如果要把投喂、记账、待办、愿望、纪念日、相册、爱心豆等都继续做深，现状不够支撑

### 3.3 后端修复目录规模

其中较核心的包括：

- `app.js`
- `feeding.js`
- `feeding_v2.js`
- `travel.js`
- `travel_photos.js`
- `beans.js`
- `finance.js`
- `todo.js`
- `anniversary.js`
- `photo.js`
- `timeline.js`
- `weather.js`

结论：

- 后端功能范围其实已经不小
- 但结构上仍然偏“修复集 / 汇总集”
- 距离长期可维护的正式服务结构还有整理工作

## 4. 关键文件证据

### 4.1 `lib/main.dart`

当前主入口文件约 **327 行**。

已确认的现状：

- App 壳层仍直接在 `main.dart` 中维护
- 当前全局注入的 Provider 只有 `Auth / Home / Travel / Theme`
- 底部导航当前承载：首页、旅行、健康、生活、我的
- 启动后仍由壳层负责版本检查与登录态切换

结构判断：

- 作为当前体量项目，这个主入口还能运行
- 但如果继续扩展，会越来越承担“调度层 + 页面层 + 状态层混合”的风险

### 4.2 `lib/services/api_service.dart`

当前 `api_service.dart` 约 **350 行**。

结构判断：

- 它已经承担了较多跨模块接口能力
- 如果后续继续把更多业务都堆进去，会演变成新的“前端总线型巨石文件”
- 更合理的方向是保留它做底层请求层，再在上层拆 domain service

### 4.3 `server_fixes/app.js`

当前后端入口约 **137 行**。

已确认的现状：

- 安全中间件、限流、静态资源、健康检查、错误处理都已经开始成型
- 路由挂载非常集中
- 已挂载的 API 范围已经覆盖 auth、travel、period、todo、finance、course、photo、mood、timeline、home、feeding、weather、version、beans、anniversary、couple 等

结构判断：

- 它已经在向“统一服务入口”靠近
- 但路由挂载的组织方式仍偏平铺
- 后续继续新增接口时，最好转向按业务域收口

### 4.4 `server_fixes/lovegirl_full_migration.sql`

当前迁移文件约 **384 行**。

已确认的方向：

- 已经包含投喂 v2 相关表方向
- 已经包含旅行路线 / 地点 / 照片等方向
- 已经体现爱心豆、通知、旅行等扩展趋势

结构判断：

- 数据模型的未来方向已经开始显现
- 但仍需要进一步和前端目标结构对齐

## 5. 当前最明显的结构问题

## 5.1 页面规模和状态管理规模失衡

这是当前最直观的问题之一。

表现为：

- 页面模块很多
- Provider 很少
- 未来如果继续把业务堆进现有 Provider，会越来越难维护

## 5.2 业务域边界已经出现重复

当前最明显的重复点包括：

- `album` 和 `photo`
- `anniversary` 和 `countdown`
- `life` 和 `tasks`
- `search` 已经脱离主线

这说明产品层面已经开始需要“收口式重构”，而不是继续平铺入口。

## 5.3 前后端都存在“中心文件继续膨胀”的风险

前端侧：

- `main.dart`
- `api_service.dart`

后端侧：

- `app.js`
- 以及继续平铺增加的 route 文件

风险不是它们现在不能用，而是：

- 每加一项功能，复杂度都在往中心聚集

## 5.4 已有功能范围不小，但尚未形成统一产品骨架

从页面目录和后端文件看，LoveGirl 其实已经不是一个“小 demo”。

问题不在于功能少，而在于：

- 功能多，但组织方式还没完全跟上
- 视觉语言、状态层、服务层、联动层都还需要统一

## 6. 对后续实施最重要的启示

## 6.1 先重组结构，再继续长功能

如果不先收口结构，后面每做一个新需求，都会更依赖历史偶然结构。

## 6.2 首页 / 投喂 / 旅行 / 我的仍然是绝对主线

从你已经确认的产品定位和当前工程状态看，这 4 个核心页仍然是最值得先做对的地方。

## 6.3 后续实施不应该再从“页面堆功能”出发

更合理的顺序应该是：

- 先按 domain 划边界
- 再补 Provider / Service
- 再统一设计系统
- 再逐页落地

## 7. 当前审计结论

截至 2026-07-17，LoveGirl 当前仓库已经具备：

- 一定规模的页面和功能基础
- 一定规模的后端与迁移基础
- 明确的核心产品主线

但还没有具备：

- 完整统一的结构骨架
- 足够细的状态管理分层
- 完整收口的信息架构
- 可直接稳定扩展的长期组织方式

因此，本轮重构不是“从零开始做一个新 App”，而是“把已经长出来的 App 收成真正能长期维护的一套产品”。
