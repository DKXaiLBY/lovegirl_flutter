# LoveGirl 迁移与回滚策略

更新时间：2026-07-17
适用阶段：方案确认阶段（当前不写业务代码）

## 1. 文档目的

这份文档回答的是：

- 后续结构调整怎么迁
- 迁到一半出问题怎么办
- 哪些地方必须保留回滚余地

它专门服务于：

- 数据库迁移
- 模块切换
- 删除旧模块
- 版本发布前的风险控制

## 2. 当前迁移起点

当前已知证据：

- `D:/lovegirl_flutter/server_fixes/lovegirl_full_migration.sql` 约 384 行
- `server_fixes` 下还有多份补丁 SQL
- 投喂存在 `feeding.js` 和 `feeding_v2.js` 双轨痕迹
- 相册 / 照片、纪念日 / 倒数日、life / tasks 都存在收口需求

结论：

- LoveGirl 不适合“一把梭全量替换”
- 更适合分批迁移、逐步切换、留回滚点

## 3. 总体迁移原则

## 3.1 先加新结构，再切换入口

顺序原则：

1. 新表 / 新字段先建立
2. 数据搬运或兼容读取逻辑准备好
3. 前端或路由入口切换
4. 旧逻辑确认无流量后再删除

## 3.2 敏感数据迁移必须先验证可解

适用范围：

- 经期
- 记账

迁移原则：

- 旧加密值必须能继续解
- 如需新字段或新结构，先验证兼容读取
- 不允许迁移后才发现旧数据解不开

## 3.3 删除模块前必须确认无依赖

重点对象：

- 全局搜索
- 卡路里追踪

典型风险：

- 前端入口已删，但后端或其他模块仍在写数据
- 记账模块仍偷偷依赖卡路里残留

## 4. 核心迁移场景

## 4.1 投喂 `v1 -> v2`

当前证据：

- `feeding.js`
- `feeding_v2.js`

迁移目标：

- 统一使用 v2 模型

推荐顺序：

1. 确认 v1 / v2 字段映射
2. 确认现有订单、商品、店铺如何迁移
3. 让前端明确只吃 v2 响应
4. 完成验证后再下线 v1

回滚点：

- 在 v2 未验证完成前，不直接破坏旧数据读取

## 4.2 相册 / 照片合并

当前证据：

- `lib/screens/photo/photo_screen.dart`
- `lib/screens/album` 当前为空目录
- 后端存在 `photo.js` 与 `travel_photos.js`

迁移目标：

- 收口到统一相册心智

推荐顺序：

1. 定义统一相册数据模型
2. 定义旅行照片在相册中的来源关系
3. 切前端入口
4. 再清理旧目录与旧命名

回滚点：

- 在统一相册未跑通前，旧照片数据仍可读

## 4.3 纪念日 / 倒数日合并

当前证据：

- `anniversary_screen.dart`
- `countdown_screen.dart`
- `countdown_form.dart`

迁移目标：

- 一个模块，两类视图

推荐顺序：

1. 先定统一模型
2. 再做视图切换
3. 再回收旧入口

回滚点：

- 新入口未稳定前，不能直接导致旧纪念日数据不可见

## 4.4 删除卡路里逻辑

当前证据：

- `finance.js` 仍有 `calorieSynced` 和 `calorie_records` 写入逻辑

迁移目标：

- 完全移除卡路里模块
- 同时不伤到记账主流程

推荐顺序：

1. 标记所有卡路里相关前后端残留
2. 先确认记账主流程不依赖这些字段
3. 再移除自动同步逻辑
4. 最后清理相关 UI / API / 数据残留

回滚点：

- 如果删除后影响记账主流程，必须能快速恢复到“记账正常、卡路里继续隐藏”的状态

## 4.5 删除全局搜索

迁移目标：

- 彻底删除全局搜索
- 改为局部搜索

推荐顺序：

1. 确认空目录和旧路由残留
2. 列出所有调用点
3. 删除全局入口
4. 保留未来局部搜索扩展位

## 5. 数据库迁移策略

## 5.1 执行前必须备份

发布前至少要准备：

- 线上数据库备份
- 当前版本 SQL 快照
- 回滚 SQL 或恢复手段

## 5.2 迁移脚本要分批

建议按主题拆：

- 投喂
- 爱心豆
- 旅行
- 回忆域
- 删除清理类

不要把所有结构改动混成一个大脚本后直接上线。

## 5.3 迁移后必须做数据抽样验证

至少抽查：

- 老投喂订单
- 老旅行地点
- 老纪念日
- 老经期记录
- 老记账记录

目标：

- 确认旧数据仍可读
- 确认加密字段仍可解

## 6. 回滚触发条件

以下任一出现，应触发回滚评估：

- 真地图主入口大面积崩溃
- 投喂主流程中断
- 旧经期或记账数据无法读取
- 更新链路失效
- 删除模块误伤其他核心流程

## 7. 回滚策略层级

## 7.1 代码回滚

适用：

- 页面 UI 改动异常
- 路由逻辑异常

要求：

- 保留明确版本边界
- 发布时记录本次变更集合

## 7.2 配置回滚

适用：

- 高德 Key 配置错误
- 环境变量缺失
- 更新地址错误

要求：

- 配置变更独立记录
- 可单独恢复，不依赖重新改代码

## 7.3 数据回滚

适用：

- 迁移导致旧数据不可读
- 新字段写入破坏原有可用性

要求：

- 先备份
- 有明确恢复窗口

## 8. 发布前必须完成的迁移验证

- 迁移脚本顺序明确
- 备份已完成
- 回滚路径明确
- 核心旧数据抽样可读
- 删除目标未误伤其他域
- 前后端新结构对齐

## 9. 当前阶段结论

截至 2026-07-17，LoveGirl 这轮重构最不适合的方式就是：

- 一次性无回退地全量替换

更稳的方式是：

- 分阶段迁移
- 保留回滚点
- 每次切一块，就验证一块

这份文档的作用，就是把这种迁移纪律提前写死。
