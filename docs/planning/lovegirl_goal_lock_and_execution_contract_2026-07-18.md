# LoveGirl 冻结执行目标与实施契约

更新时间：2026-07-18
适用阶段：实施前冻结 / 后续执行唯一基线

## 1. 这份文档解决什么问题

前面的规划文档已经很多，也已经把方向讨论得足够完整。

这份文档不再继续发散，而是把已经确认的内容冻结成一份可以直接执行的目标契约，用来回答 4 个问题：

1. 这轮到底要做完什么
2. 哪些东西明确不做或后置
3. 实施顺序怎么排
4. 什么状态才算真正完成

后续如果继续推进实现，应优先以这份文档作为执行口径，再回看对应的分文档。

## 2. 冻结后的总目标

把 LoveGirl 从一个功能堆叠、视觉不统一、旅行地图方案不稳定、局部中文和交互质量不可靠的私人情侣 App，收口成一个：

- 视觉统一
- 中文干净
- 核心链路可用
- 地图能力稳定
- 模块边界清楚
- 后续方便继续加功能
- 可以真机验收
- 最终可以发布的新版本

这轮不是做“更多功能”，而是做“更完整、更像作品、更能长期维护”的版本。

## 3. 本轮产品范围冻结

### 3.1 强保留模块

- 首页
- 投喂站
- 旅行地图
- 我的
- 私密聊天
- 伴侣绑定
- 经期管理
- 记账
- 课程表
- 心情日记
- 恋爱时光轴
- 待办
- 愿望清单

### 3.2 合并模块

- `纪念日 + 倒数日` 合并为同一时间提醒域
- `相册 + 照片` 合并为同一回忆素材域

### 3.3 不强行合并，但做主从整理

`待办` 和 `愿望清单` 不直接合成一个模块。

原因：

- 你的判断是成立的：待办偏短期执行，愿望清单偏长期想实现
- 两者用户心智不同，强合并反而会让日常使用变糊
- 但两者底层能力可以共享，比如状态、标签、完成记录、首页摘要入口

因此本轮采用：

- 产品层保留两个入口
- 结构层归到同一个 `Life Domain`
- 能复用的数据结构和组件尽量复用

### 3.4 明确删除模块

- 全局搜索
- 卡路里追踪

删除标准不是“入口隐藏”，而是：

- 路由移除
- 页面移除
- Provider / Service / 模型引用清理
- 不再保留误导性的残余入口

## 4. 视觉目标冻结

### 4.1 统一视觉方向

本轮视觉方向冻结为你已经确认的那条：

- 回忆票根
- 专属菜单
- 温暖纸感
- 简约但不冷
- 精致浏览感

不是：

- 办公软件感
- 过粉过甜的模板情侣风
- 大面积营销页风格
- 一堆通用图标拼起来的首页

### 4.2 4 个核心页面的视觉要求

#### 首页

目标感觉：

- 第一眼是被认真照顾过的首页
- 信息有层次，但不吵
- 像你们的生活摘要，不像功能目录

必须具备：

- 恋爱天数主头部
- 天气卡片，含温度与体感温度，且不溢出
- 回忆票根区
- 今日摘要区
- 快捷入口区

#### 投喂站

目标感觉：

- 像真的在点你给她准备的专属菜单
- 商品浏览过程要有“被宠”的感觉
- 不是普通商城，也不是后台列表

必须具备：

- 店铺列表和商品列表的菜单感层次
- 她自己新增的想吃项有明显标记
- 下单、接单、准备、配送、完成链路清楚
- 爱心豆只做奖励感知，不阻断下单

#### 旅行地图

目标感觉：

- 第一眼像真正地图产品
- 地图是主角，票根是信息容器
- 点击地点时有流畅反馈，不像静态截图

必须具备：

- 高德原生地图模式
- 蓝点 / 定位 / 地图平滑移动
- 地点详情票根化
- 路线预览
- 两人共同编辑痕迹

#### 我的

目标感觉：

- 是关系资料页和个人偏好页
- 不堆一排无意义工具入口
- 有“你们两个人的资料感”，不是系统设置页翻版

必须具备：

- 个人信息 / 伴侣信息
- 爱心豆 / 关系状态 / 关键统计
- 资料管理、通知、版本、隐私等二级设置入口

## 5. 地图方案冻结

旅行地图本轮正式废弃 `flutter_map + 高德瓦片` 路线，统一改为：

- Flutter 端：`amap_flutter_map`
- Android 端：高德 Android 地图 SDK
- 服务查询：高德 Web 服务 API 由后端代理

### 5.1 本轮地图必须做到

- 真地图正常加载
- 打开高德地图模式不闪退
- 定位权限流程清楚
- 蓝点、方向、精度圈正常
- 点击地点平滑移动
- Marker 高亮与底部详情联动
- 路线预览至少支持步行 / 驾车 / 公交
- 天气、地理编码、POI 查询通过后端代理

### 5.2 本轮可以后置的地图能力

- 完整导航 SDK 深接
- 导航语音播报
- 更复杂的离线策略
- iOS 地图对齐

这些不是放弃，而是放到下一波，不阻塞本轮主目标闭环。

## 6. 功能策略冻结

### 6.1 投喂站

本轮目标不是继续做“全量店铺抓取”，而是改成更可控、更像私人菜单的体系：

- 你预置常点商品
- 她可以补充自己想吃的东西
- 自增商品有特殊标识
- 真实下单平台、真实金额、备注要记录
- 履约状态要贴近真实外卖流程
- 催单变成真实通知，而不是纯计数

### 6.2 爱心豆

爱心豆不再承担“能不能下单”的门槛作用，而是做：

- 奖励感知
- 抵扣感知
- 关系互动反馈

冻结原则：

- 不阻止她下单
- 可以按比例抵扣真实金额的一部分
- 必须有流水
- 必须能被首页 / 投喂站 / 我的页读到

### 6.3 旅行地图扩展

本轮纳入：

- 路线规划
- 旅行花费记录
- 自动同步到记账
- 景点详情天气 / 交通 / 地址等信息
- 成就沉淀到时光轴 / 首页 / 月度报告
- 同一地点的双方共同编辑痕迹

### 6.4 模块联动

本轮联动目标不是“多”，而是“有意义且不突兀”。

优先成立的联动：

- 投喂站 -> 记账
- 旅行 -> 记账
- 旅行 -> 时光轴
- 投喂站里程碑 -> 时光轴
- 经期 -> 投喂站推荐
- 纪念日 -> 首页提醒
- 课程表 -> 首页摘要
- 待办 -> 首页摘要

### 6.5 首页摘要

首页不是单独做业务，而是只读聚合：

- 今日天气
- 今日课程
- 待办摘要
- 回忆票根
- 旅行摘要
- 恋爱关键天数

这样以后新增模块时，只需要补一个摘要卡片接入点，不需要改首页主结构。

## 7. 结构可添加性契约

后续新功能如果要加入，必须满足下面这套接入规则。

### 7.1 前端

每个新模块都应尽量具备自己的：

- `screen`
- `widget`
- `provider`
- `service`
- `model`

禁止继续扩大“一个 screen 里塞全部逻辑”的做法。

### 7.2 后端

后端按下面 4 层整理：

- `routes`
- `services`
- `middleware`
- `config / db`

Web Key 留在后端环境变量，不进入 Flutter 前端。

### 7.3 聚合层

首页、月报、时光轴这类聚合模块只负责读结果，不直接承担各业务域写入逻辑。

推荐采用：

- 业务域自己写主数据
- 联动通过统一同步层或明确的事件写入

### 7.4 删除规则

以后任何模块如果删除，不允许只删 UI 入口。

必须同时检查：

- 路由
- Provider
- Service
- 数据表 / 迁移
- 首页摘要
- 我的页入口
- 搜索或联动引用

## 8. 实施顺序冻结

### P0：工程基线与止血

1. 清理删除目标的残留引用
2. 处理首页 / 投喂站 / 旅行地图中的乱码和明显错位
3. 修复旅行地图高德模式闪退
4. 梳理后端路由结构和缺失依赖
5. 建立后续可继续落地的 Provider / Service 骨架

### P1：核心体验落地

1. 首页按票根方向重构成中文正式版
2. 投喂站改成专属菜单体验
3. 旅行地图改成高德原生主地图方案
4. 我的页改成关系资料中心

### P2：模块收口与联动

1. 合并纪念日 / 倒数日
2. 合并相册 / 照片
3. 建立投喂、旅行、记账、时光轴联动
4. 爱心豆余额与流水接入

### P3：发布闭环

1. 对抗式审查
2. 真机验收
3. 服务器部署
4. 版本号校准
5. APK / 更新发布

## 9. 每个阶段的验收标准

### M1 工程基线清理完成，必须同时满足

- 全局搜索与卡路里链路已从代码结构中清掉
- 空目录、废弃入口、误导性残留已识别并清理
- 后端当前真实结构问题被查清
- 后续实施不再被“旧路径假象”干扰

### M2 UI 基线完成，必须同时满足

- 首页、投喂站、旅行地图、我的页视觉语言一致
- 中文文案无乱码
- 天气卡片不溢出
- 首页不再像通用模板

### M3 地图主链路完成，必须同时满足

- 打开高德真地图不闪退
- 定位、蓝点、移动、标记、详情联动正常
- 路线预览可用
- 天气与 POI 查询可用

### M4 投喂主链路完成，必须同时满足

- 商品浏览、下单、状态流转可走通
- 真实平台信息可记录
- 催单通知链路成立
- 爱心豆抵扣逻辑不阻断下单

### M5 联动与收尾完成，必须同时满足

- 投喂、旅行、记账、时光轴联动至少首批成立
- 纪念日 / 倒数日、相册 / 照片完成收口
- 首页摘要能稳定读取核心模块

### 发布完成，必须同时满足

- 通过对抗式审查
- 通过真机验收
- 新版本安装升级正常
- 服务器端与客户端版本匹配
- 没有明显崩溃、乱码、空白主流程

## 10. 当前已知高风险点

### P0 风险

- 旅行地图真机闪退
- 后端 `server_fixes` 结构不完整，路由挂载与文件布局不一致
- 已删除模块可能还有残余引用
- UI 已有改动与目标设计图存在偏差

### P1 风险

- 中文编码和旧文案清理不彻底
- 首页聚合时继续把业务逻辑写回首页
- 投喂站状态流如果硬编码，会导致后续接真实履约难以维护

### 当前处理原则

- 先止血，再扩展
- 先修主链路，再补边缘模块
- 先统一结构，再做大量视觉润色

## 11. 执行约束

后续进入实现时，必须遵守：

- 不为了快而跳过真机验证点
- 不在 UI 还没对齐时就急着构建正式 APK
- 不在高德地图稳定性没确认前就视为旅行地图完成
- 不把“入口能打开”当成“功能已完成”
- 不把“局部页面好看了”当成“整套视觉已经统一”

## 12. 这份目标文档之后怎么用

后续真正执行时，建议按下面顺序工作：

1. 先看这份冻结执行目标
2. 再看 `lovegirl_phase1_baseline_cleanup_worklist.md`
3. 再看 `lovegirl_master_delivery_control_board.md`
4. 每完成一段都留下实现证据
5. 最后再进入真机验收、部署和发布

一句话说清楚：

从现在开始，LoveGirl 的目标不是“继续讨论”，而是按这份契约把它一段一段做成。
