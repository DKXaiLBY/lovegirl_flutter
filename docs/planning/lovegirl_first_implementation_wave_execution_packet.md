# LoveGirl 首批实现波次执行包（M1-M3）

更新时间：2026-07-17
适用阶段：从方案确认切入实现阶段前使用

## 1. 这份文档的定位

前面的文档已经解决了：

- 做什么
- 先后顺序
- 哪些要保留、合并、删除
- 哪些风险和阻断项存在

这份文档再往前走半步，解决的是：

- 第一波真正开工时，一项项先做什么
- 每项任务的输入文件和输出结果是什么
- 每项任务完成后，应该用什么证据证明自己没有走偏

它不是新的产品方案，而是实现阶段前 3 个里程碑的执行包。

## 2. 适用范围

本执行包只覆盖下面三个阶段：

- `M1 工程基线清理`
- `M2 设计系统统一`
- `M3 首页重构`

原因很简单：

- 这三步是整个重构的起跑姿势
- 起跑姿势不对，后面的投喂站、旅行地图、我的页都会跟着偏

## 3. 使用方式

后续开始写代码时，建议按下面顺序配合使用：

1. 先看 [LoveGirl-全面修复与重构目标文档.md](D:/lovegirl_flutter/LoveGirl-全面修复与重构目标文档.md)
2. 再看 [README.md](D:/lovegirl_flutter/docs/planning/README.md)
3. 再看 [lovegirl_implementation_kickoff_brief.md](D:/lovegirl_flutter/docs/planning/lovegirl_implementation_kickoff_brief.md)
4. 真正执行时，对照这份文档逐项推进

## 4. 总体推进原则

### 4.1 每个任务都必须可验收

不要用“差不多整理好了”这种说法。

每个任务至少要有：

- 明确输入文件
- 明确产出
- 明确验证方式

### 4.2 先降噪，再重构

前 3 步不以“加功能”为目标，而是先把噪音降下来：

- 删无效入口
- 收口重复责任
- 统一视觉基础件
- 把首页做成之后所有页面的母版示范

### 4.3 每完成一个工作包都要留下证据

证据可以是：

- 修改后的文件
- `flutter analyze` 结果
- 真机或模拟器截图
- 文档中的责任映射更新

没有证据，就不算完成。

## 5. Wave 1：M1 工程基线清理

## 5.1 M1 的目标

把工程从“历史残留太多、边界模糊、后续一改就扯一片”的状态，清理成可以安心继续施工的底座。

## 5.2 M1 工作包

### W1：主入口责任拆分基线

输入文件：

- `D:/lovegirl_flutter/lib/main.dart`

目标：

- 明确哪些逻辑属于 App Shell
- 明确哪些逻辑属于具体页面
- 标记壳层后续迁移边界

完成后应得到：

- `main.dart` 责任拆分笔记
- 后续迁移到 `app/` 目录的候选逻辑清单

验证：

- 能明确说出登录态、底部导航、版本检查、页面切换各自归属

### W2：Provider 基线清点

输入目录：

- `D:/lovegirl_flutter/lib/providers`

目标：

- 列出当前已有 Provider 的真实责任
- 列出缺失的 domain Provider
- 标记未来每个 Provider 服务哪个模块

完成后应得到：

- Provider 现状表
- Provider 缺口表
- Provider 与模块的映射表

验证：

- 任何一个核心模块都能回答“后续它归谁管理状态”

### W3：Service 基线清点

输入目录：

- `D:/lovegirl_flutter/lib/services`

目标：

- 把 `ApiService` 重新定义为底层网络层
- 标记未来应拆出去的 domain service
- 避免继续把新接口都堆进单个 service 文件

完成后应得到：

- Service 现状表
- Service 拆分目标表

验证：

- 能明确区分 transport、domain service、notification、logging 的边界

### W4：删除目标残留排查

输入范围：

- 前端 `search / health / life / tasks / main.dart / 路由入口`
- 后端 `server_fixes` 下相关 route 与联动

目标：

- 盘点全局搜索残留
- 盘点卡路里残留
- 明确删除时会波及哪些调用链

完成后应得到：

- 搜索残留清单
- 卡路里残留清单
- 删除影响面说明

验证：

- 删除方案不止删 UI 入口，还覆盖 provider、service、API、route、联动

### W5：合并目标迁移源排查

输入范围：

- `photo / album`
- `anniversary / countdown`
- `life / tasks`

目标：

- 识别每一组将来合并时的源文件
- 识别重复职责和冲突入口

完成后应得到：

- 相册合并迁移源清单
- 纪念日合并迁移源清单
- Life 域责任边界表

验证：

- 能明确说出“以后保留哪个入口、迁走哪些数据和 UI 责任”

### W6：后端路由主线盘点

输入文件：

- `D:/lovegirl_flutter/server_fixes/app.js`
- `D:/lovegirl_flutter/server_fixes/*.js`

目标：

- 盘点真实挂载的 route
- 标记主线 route、删除 route、待统一 route
- 确定 feeding v1/v2 的切换边界

完成后应得到：

- route 盘点表
- feeding 双轨切换说明

验证：

- 能明确说出“哪些接口必须保住、哪些接口要清掉、哪些接口结构要统一”

## 5.3 M1 完成标准

满足下面这些才算 M1 完成：

- 重复入口和空目录的处理路径已经明确
- Provider / Service 缺口已经被结构化列出
- 搜索和卡路里删除影响面已经盘清
- 后端路由的保留 / 删除 / 统一边界已经盘清
- 后续进入 UI 或状态重构时，不会再因为“先找不到边界”停住

## 6.3 M2 完成标准

## 8. M1-M3 验证矩阵

| 波次 | 核心验证问题 | 证据类型 |
|------|---------------|----------|
| M1 | 我们是否已经盘清后续重构边界？ | 责任表、残留清单、route 盘点 |
| M1 | 删除目标是否只停留在口头？ | 残留链路盘点、影响面说明 |
| M2 | UI 是否已经有统一骨架？ | 主题文件、通用组件、页面对比截图 |
| M2 | 四大页面是否开始长得像一个产品？ | 首页 / 投喂站 / 旅行 / 我的并排截图 |
| M3 | 首页是否真的接近确认方向？ | 首页截图、文案检查、天气卡边界检查 |
| M3 | 中文和状态表现是否干净？ | UI 截图、错误态 / 空态对照 |
