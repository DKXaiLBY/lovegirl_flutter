# LoveGirl 模块清理、合并、删除清单

更新时间：2026-07-17
适用阶段：方案确认阶段（当前不写业务代码）

## 1. 文档目的

这份文档专门服务于后续的工程基线清理阶段。

它回答的是：

- 哪些模块要保留
- 哪些模块要合并
- 哪些模块要删除
- 清理时要删到什么程度才算真的删干净

## 2. 保留模块

这些模块不是“先暂时留着”，而是这轮重构的核心资产。

### 核心主线

- 首页
- 投喂站
- 旅行地图
- 我的页

### 互动与关系

- 私密聊天
- 伴侣绑定

### 生活

### 回忆

- 心情日记
- 恋爱时光轴
- 相册（合并后）
- 纪念日（合并后）

## 3. 合并模块

## 3.1 `album + photo -> 相册`

目标：

- 把图片资产统一收口

清理要求：

- 前端只保留一个主要图片入口
- 后端照片相关接口按统一相册模型收口
- 旅行照片作为相册中的来源分支，不再形成平行产品心智

验收标准：

- 导航或入口不再同时出现“相册”和“照片”两套重复概念
- 数据模型和接口归属清楚

## 3.2 `anniversary + countdown -> 纪念日`

目标：

- 把纪念事件和倒数目标统一到一个模块下

清理要求：

- 前端统一到同一模块入口
- 视图内允许区分“纪念日 / 倒数日”
- 旧入口逐步退场

验收标准：

- 导航结构里不再并行维护两个高度相似的模块

## 3.3 `待办 + 愿望清单`

说明：

- 不做物理删除式合并
- 做同域收口式整合

目标：

- 两者都放入 `life` 域
- 共享部分结构和组件
- 继续保留不同语义

验收标准：

- 在产品心智上清楚区分“今天要做”和“长期想实现”
- 不再散落为两个彼此孤立的系统

## 4. 删除模块

## 4.1 全局搜索

删除原因：

- 使用价值低
- 维护成本高
- 与当前产品主线关系弱

删除范围要求：

- 删除前端入口
- 删除 screen / widget / menu 残留
- 删除 Provider 残留
- 删除 `ApiService` 中相关方法
- 删除后端搜索 route
- 删除数据库或配置中的无用残留

替代策略：

- 在投喂、旅行、相册等模块内做局部搜索

删除完成标准：

- 全项目中不再存在对“全局搜索模块”的真实依赖

## 4.2 卡路里追踪

删除原因：

- 与情侣 App 核心主线关系弱
- 不值得继续占结构位置

删除范围要求：

- 删除页面入口
- 删除交互入口
- 删除 Provider / Service / API 残留
- 删除后端接口与数据残留

删除完成标准：

- App 不再暴露任何卡路里相关入口
- 构建与运行不依赖其存在

## 5. 需要重点排查的重复或边界模糊点

这些未必全部删除，但在工程基线阶段必须排查清楚：

- `life` 与 `tasks` 的职责边界
- `settings` 与 `profile` 的职责边界
- `common` 中是否混入了具体业务组件
- `admin` 是否和正式用户端结构混在一起
- `travel_photos` 与 `photo` 的后端关系
- `feeding.js` 与 `feeding_v2.js` 的替换边界

## 6. 清理顺序建议

建议清理时按下面顺序推进：

1. 先列依赖，再删入口
2. 先删前端暴露，再删后端残留
3. 先确认替代方案，再删旧能力
4. 每删一个模块，都要补回归检查

## 7. 清理完成的判断标准

一个模块只有在下面这些条件都满足后，才算“真的删干净”：

- 导航和页面入口没有了
- 代码搜索不到仍在调用的业务逻辑
- Provider / Service / API 残留被清理
- 后端 route 不再对外提供该能力
- 构建和运行不受影响

## 8. 当前阶段结论

截至 2026-07-17，本轮重构在模块处理上的明确方向是：

- 强保留核心主线
- 合并高重叠模块
- 删除低价值模块
- 对边界模糊模块先审计再动刀
