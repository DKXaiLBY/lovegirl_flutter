# LoveGirl 安全与数据完整性方案

更新时间：2026-07-17
适用阶段：方案确认阶段（当前不写业务代码）

## 1. 文档目的

这份文档解决的是“重构时哪些数据和安全要求绝对不能丢”。

前面的方案已经把：

- 产品方向
- UI 方向
- 模块结构
- 实施顺序

写得比较完整了。

但像下面这些东西，如果不单独固定，很容易在实现阶段被挤掉：

- 经期数据加密
- 记账金额加密
- 鉴权和角色权限
- 文件上传校验
- 推送与催单一致性
- 迁移过程中不丢数据

## 2. 当前已知证据

### 2.1 经期模块已经在走敏感数据加密存储

当前文件：

- `D:/lovegirl_flutter/server_fixes/period.js`

已见到的证据：

- 注释明确写了“敏感数据加密存储”
- 代码通过 `encrypt / decrypt` 处理：
  - 开始日期
  - 结束日期
  - 疼痛等级
  - 症状
  - 用药
  - 备注

说明：

- 经期模块不是普通表单模块
- 重构时必须把这条加密链完整保住

### 2.2 记账模块已经在走金额加密存储

当前文件：

- `D:/lovegirl_flutter/server_fixes/finance.js`

已见到的证据：

- 注释明确写了“金额加密存储”
- 代码通过 `encrypt / decrypt` 处理：
  - `amount_encrypted`
  - `description_encrypted`

说明：

- 记账金额与描述都不能在重构时回退成明文方案

### 2.3 记账模块仍残留卡路里联动逻辑

当前文件：

- `D:/lovegirl_flutter/server_fixes/finance.js`

已见到的证据：

- 仍存在 `calorieSynced`
- 仍存在向 `calorie_records` 自动写数据的逻辑

说明：

- 这和“卡路里追踪确定删除”直接冲突
- 后续删除卡路里模块时，必须把这条残留链路一起清干净

## 3. 不可退让的安全底线

## 3.1 敏感数据不能回退成明文

以下数据在重构后依然必须加密存储：

- 经期记录
- 痛经记录
- 记账金额
- 记账备注中的敏感内容

执行原则：

- 保持现有 `encrypt / decrypt` 兼容
- 重构中不得先为了赶进度改回明文字段
- 如需升级加密实现，必须保证旧数据可解

## 3.2 加密方案必须明确落到实现要求

编码阶段必须遵守：

- 经期数据、记账金额继续走 AES-256-GCM 级别的加密方案
- 加解密逻辑不能在重构时被遗漏
- 不能让旧数据因为密钥或格式变化而不可读

说明：

- 这不是可选增强项，而是重构保真要求

## 3.3 所有敏感路由默认鉴权

以下业务域必须默认经过鉴权：

- 经期
- 记账
- 投喂订单
- 旅行地点与照片
- 聊天
- 伴侣绑定
- 爱心豆
- 时光轴

执行原则：

- 默认加 `auth` 中间件
- 不是前端隐藏入口就算安全
- 必须在路由层做校验

## 3.4 角色权限必须后端校验

需要区分的至少包括：

- 女友专属功能
- 男友履约操作
- 伴侣双方都可见但各自只能编辑自己内容的场景

典型场景：

- 经期数据仅女友可写
- 投喂男友端履约字段不能让无权限用户随便改
- 同地点双人备注必须区分写入归属

## 3.5 文件上传必须校验

涉及：

- 相册
- 旅行照片
- 可能的凭证图片

至少要有：

- 类型校验
- 大小限制
- 存储路径控制
- 非法文件拒绝

## 3.6 日志不能泄露密钥、Token、敏感明文

重构时要避免：

- 把解密后的经期内容打进日志
- 把金额明文打进错误日志
- 把 Token、密钥、签名信息打进日志

## 4. 数据完整性要求

## 4.1 重构不是新建空系统

LoveGirl 当前不是 demo。

所以这次重构必须满足：

- 旧数据尽量可继承
- 旧密文字段可继续解读
- 旧订单、旧旅行、旧纪念日数据不因结构调整而报废

## 4.2 迁移期间要允许兼容窗口

典型场景：

- `feeding.js` 向 `feeding_v2.js` 迁移
- `anniversary + countdown` 合并
- `photo + album` 合并
- 删除卡路里逻辑时保住记账主流程

执行原则：

- 先建新结构
- 再做数据搬运
- 再切换入口
- 最后移除旧残留

## 4.3 删除模块时不能误伤其他域

重点风险：

- 卡路里虽然要删，但现在还挂在 `finance.js`
- 搜索虽然要删，但要确认没有模块仍在依赖它

执行原则：

- 删除前先画依赖
- 删除后做接口和运行回归

## 5. 推送与通知完整性要求

投喂站催单改成真实提醒后，必须满足：

- 通知触发和订单状态不互相打架
- 失败时有日志可追
- 不会因为重复点击造成通知风暴
- 不会出现数据写成功但通知链完全不可追的黑盒状态

建议要求：

- 催单事件单独记录
- 做频率限制
- 做幂等控制或最小间隔控制

## 6. 安全专项实施要求

## 6.1 Phase 1 应产出的安全清单

在 `M1` 阶段至少要列清：

- 哪些表字段是敏感字段
- 哪些路由必须鉴权
- 哪些场景要做角色权限
- 哪些上传入口需要校验
- 哪些旧逻辑与删除目标冲突

## 6.2 M10 后端统一阶段必须落实的内容

- 加密逻辑保留与迁移
- 权限中间件补齐
- 上传校验补齐
- 日志脱敏规则明确
- 删除卡路里残留链路

## 6.3 M11 对抗式审查必须专项检查

- 经期和记账是否仍加密
- 非本人能否访问敏感记录
- 上传是否可绕过类型限制
- Token 过期后是否处理正常
- 是否有敏感信息泄露到日志
- 推送失败时数据是否一致

## 7. 完成标准

只有满足下面这些条件，安全与数据完整性方案才算真正落地：

- 经期与记账敏感数据继续加密
- 旧数据可读取
- 敏感路由都经过鉴权
- 关键角色权限在后端有校验
- 上传校验成立
- 删除卡路里残留后不影响记账主流程
- 对抗式审查通过安全专项

## 8. 当前阶段结论

截至 2026-07-17，LoveGirl 的安全风险并不在于“完全没做保护”，而在于：

- 已经有一部分保护链路存在
- 但如果重构时没有单独盯住，很容易出现回退或漏迁移

这份文档的作用，就是把这些不能退的底线钉住。
