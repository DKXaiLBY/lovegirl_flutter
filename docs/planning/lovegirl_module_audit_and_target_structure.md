# LoveGirl 模块审计与目标结构

更新时间：2026-07-17
适用阶段：方案确认阶段（当前不写业务代码）

## 1. 当前仓库结构观察

### 1.1 当前前端 screen 目录

当前 `lib/screens` 下可见模块目录：

- `admin`
- `album`
- `anniversary`
- `auth`
- `chat`
- `common`
- `countdown`
- `couple`
- `feeding`
- `health`
- `home`
- `life`
- `mood`
- `photo`
- `profile`
- `search`
- `settings`
- `tasks`
- `timeline`
- `travel`
- `version`

从这里能直接看出几个问题：

- 模块已经很多，但边界并不完全收束
- `album` 和 `photo` 存在职能重叠
- `anniversary` 和 `countdown` 存在职能重叠
- `search` 已经失去产品意义
- `life` 与 `tasks` 之间存在未来继续重叠的风险

### 1.2 当前前端 provider 目录

当前 `lib/providers` 只有：

- `auth_provider.dart`
- `home_provider.dart`
- `theme_provider.dart`
- `travel_provider.dart`

这和现有页面规模明显不匹配。

结论：

- 页面层已经长大
- 状态管理层还没有同步成长
- 继续在现状上叠功能，会越来越难维护

### 1.3 当前后端 server_fixes 目录

当前 `server_fixes` 已包含较多业务文件：

- `app.js`
- `feeding.js`
- `feeding_v2.js`
- `travel.js`
- `travel_photos.js`
- `beans.js`
- `finance.js`
- `todo.js`
- `mood.js`
- `timeline.js`
- `anniversary.js`
- `course.js`
- `weather.js`
- `notifications.js`
- `couple.js`
- 等

同时存在：

- 迁移 SQL
- 部署脚本
- 修补脚本
- 历史兼容文件

结论：

- 你已经有了“未来完整后端”的雏形
- 但还没有被整理成一个长期可维护的结构

## 2. 模块审计结论

## 2.1 首页

状态：必须保留，且必须升为第一优先级

理由：

- 首页决定第一眼感受
- 也是后续模块联动的摘要入口
- 你已经明确希望首页像一张精致的恋爱生活票根，而不是功能导航页

目标：

- 第一屏就有情绪价值
- 同时还能承载天气、今日事项、回忆、旅行、生活摘要

## 2.2 投喂站

状态：核心灵魂功能，必须强保留

理由：

- 这是整个 App 最独特、最有你个人动机的功能
- 不只是“点单”，而是“虚拟点单 + 真实履约”
- 也是未来最值得继续打磨和联动的模块

当前风险：

- 前后端版本不完全统一
- 商品来源策略需要收口
- UI 需要真正摆脱商城感

目标：

- 她点单时觉得“这是真的在叫你买”
- 你履约时有完整记录与状态链路

## 2.3 旅行地图

状态：核心灵魂功能，必须强保留

理由：

- 既有实用价值，也能沉淀共同记忆
- 未来很适合做出你们这款 App 的第二个辨识度

当前风险：

- 旧瓦片方案体验差
- 真地图模式稳定性要求高
- 旅行功能正在从“地点列表”升级为“地图产品”

目标：

- 想去、规划、打卡、沉淀，一条链完整闭环

## 2.4 经期管理

状态：保留

理由：

- 有实际使用价值
- 与情侣照顾场景天然相关
- 可以与投喂站做轻联动

注意：

- 敏感数据安全和温和表达优先

## 2.5 私密聊天

状态：保留

理由：

- 情侣 App 有真实场景
- 适合承接日常互动
- 未来还可和时光轴轻联动

注意：

- 不需要变成大而全 IM
- 重点是私密、稳定、好看

## 2.6 伴侣绑定

状态：保留

理由：

- 是双人关系模型的基础设施
- 也是权限、同步、首页关系状态的前提

## 2.7 记账

状态：保留

理由：

- 对情侣生活确实有用
- 与投喂、旅行天然可联动

注意：

- 不要做成金融工具
- 只要清楚、轻量、稳定

## 2.8 待办

状态：保留

理由：

- 日常计划有真实需求
- 可以给首页与爱心豆提供稳定数据源

## 2.9 愿望清单

状态：保留，但下沉到 Life 域内

理由：

- 你的判断是对的：愿望清单和待办确实不是同一种东西
- 它不是立刻执行型，而是长期期待型

目标：

- 与待办共享部分能力
- 不强行做成一个列表

## 2.10 课程表

状态：保留

理由：

- 你们都还在上学
- 首页展示“今日课程 / 下一节课”有明显价值

## 2.11 心情日记

状态：保留

理由：

- 对情侣关系有表达价值
- 适合沉淀到首页或月度报告

## 2.12 相册 / 照片

状态：合并

理由：

- 业务都是图片资产管理
- 当前拆分意义不大

目标：

- 统一成一个“相册”
- 再按来源分组

## 2.13 纪念日 / 倒数日

状态：合并

理由：

- 数据结构接近
- 页面交互接近
- 拆开会重复维护

目标：

- 一个模块，两种视图

## 2.14 恋爱时光轴

状态：保留

理由：

- 是“共同记忆沉淀层”
- 很适合承接投喂、旅行、照片、聊天精选

## 2.15 全局搜索

状态：删除

理由：

- 使用价值低
- 维护成本高
- 更适合改为模块内搜索

## 2.16 卡路里追踪

状态：删除

理由：

- 和整套 App 主线关系弱
- 不值得继续占用结构和维护成本

## 3. 目标信息架构

## 3.1 底部导航建议

底部层级建议继续围绕 5 个主入口，但每个入口的职责更清楚：

1. 首页
2. 互动
3. 旅行
4. 生活
5. 我的

说明：

- 如果当前工程上暂时仍保留现有 5 tab 结构，也可以先不硬切导航名
- 但最终信息架构应靠近这个逻辑

## 3.2 互动域

建议承接：

- 投喂站
- 私密聊天
- 心情日记
- 纪念日

这类功能都偏“关系互动”。

## 3.3 旅行域

承接：

- 地图主页
- 想去地点
- 路线
- 花费
- 成就
- 旅行相册 / 小票

## 3.4 生活域

承接：

- 待办
- 愿望清单
- 记账
- 课程表

## 3.5 回忆层

回忆不一定单独占一个 tab，也可以通过：

- 首页回忆票根
- 旅行打卡沉淀
- 相册
- 时光轴
- 月度报告

这几块共同承担。

## 4. 可扩展目标结构

## 4.1 前端扩展规则

未来新增一个功能时，应按下面格式接入：

1. 新增一个 domain 或子 domain
2. 放入自己的 `models / services / providers / widgets / screens`
3. 如需首页摘要，则只给首页暴露 summary 接口
4. 如需联动，则接入统一 linkage 层
5. 如需视觉组件，则优先复用设计系统，不单独发明

## 4.2 后端扩展规则

未来新增一个模块时：

1. 先定义表
2. 再定义 route
3. 再写 service
4. 再补权限与校验
5. 再开放给前端

不再继续出现“先在前端写页面，再到后端临时补洞”的模式。

## 4.3 数据扩展规则

所有新表都应明确：

- 所属业务域
- 创建者 / 所属用户
- 与情侣关系的关联方式
- 是否可首页摘要
- 是否可沉淀到时光轴
- 是否可触发爱心豆

## 5. 这一轮最值得优先做对的事情

不是把每个页面都粗糙翻新一遍，而是把下面这些真正做扎实：

### P0

- 首页还原确认方向
- 投喂站主流程和视觉语言统一
- 旅行地图高德方案稳定
- 我的页变成关系资料夹
- 中文乱码清理

### P1

- 生活域结构稳定
- 相册 / 纪念日合并完成
- 模块联动骨架建立
- 爱心豆系统结构落地

### P2

- 成就
- 月度报告
- 随机回忆
- 桌面小组件

这些不是不要做，而是优先级低于核心链路稳定。

## 6. 本文档结论

LoveGirl 下一阶段不应该继续“哪里不对修哪里”，而应该进入：

- 有主结构
- 有模块边界
- 有保留 / 合并 / 删除策略
- 有后续扩展规则

的系统化重构阶段。

这个模块审计结论，将作为后续实施顺序和代码改造范围的依据。
