# LoveGirl 风险登记与缓解方案

更新时间：2026-07-17
适用阶段：方案确认阶段（当前不写业务代码）

## 1. 文档目的

这份文档用来提前回答两件事：

1. 后续实施最容易在哪些地方翻车
2. 每类风险应该怎么提前压住

它不替代需求文档，也不替代验收文档，而是专门服务于：

- 排优先级
- 安排验证顺序
- 提前发现“不能拖到最后才处理”的问题

## 2. 风险等级定义

- `P0`：会直接阻断真机验收、发布或核心流程可用性
- `P1`：不会立刻阻断发布，但会严重影响体验或返工成本
- `P2`：暂时不致命，但会持续拖慢项目推进

## 3. 风险清单

## 3.1 地图真机稳定性风险

- 等级：`P0`
- 领域：旅行地图 / Android 真机 / 高德 SDK

描述：

- 当前地图方向已经明确改为高德 Android 原生 SDK
- 但是否在真实 Android 设备上稳定工作，不能只靠静态代码和本地编译证明

可能表现：

- 打开真地图崩溃
- 地图空白
- 蓝点不显示
- 方向箭头异常
- 权限链路有缺口

缓解方案：

- 把真机地图验收放到发布前的阻断位，而不是末尾顺手看看
- 尽早准备好 Android 地图 Key、导航 Key、Web 服务 Key
- 在实现期保留“无地点”和“无权限”兜底态
- 每次地图层大改后都做最小真机回归

最终证据：

- 真机录屏
- 无崩溃日志
- 定位与点位截图

## 3.2 UI 与确认参考图偏离风险

- 等级：`P0`
- 领域：首页 / 投喂站 / 旅行 / 我的

描述：

- 这轮重构里，用户对 UI 方向已经有明确确认
- 如果后续实现时只“看起来更精致”，但没有真正贴近已确认方向，就会出现反复返工

可能表现：

- 首页重新变回功能看板
- 图标气质回退成普通 Material 页面
- 我的页重新变成设置列表
- 投喂站重新像商城

缓解方案：

- 以确认参考图作为母版
- 先改共享设计系统，再改页面
- 每完成一个核心页都要抓图对照

最终证据：

- 核心页截图对照
- 设计规范与页面实现一致性检查

## 3.3 中文文案回退风险

- 等级：`P0`
- 领域：全局

描述：

- 当前项目历史上反复出现过乱码、英文占位、混合文案问题
- 这是直接破坏成品感的高频风险

可能表现：

- 页面局部乱码
- 部分按钮回退成英文
- 错误提示语不统一

缓解方案：

- 在基线清理阶段列出高风险文件
- 核心页改动后必须重新扫文案
- 发布前增加“中文可读性”专项核对

最终证据：

- 文案扫描结果
- 关键页面截图

## 3.4 投喂站主流程复杂度风险

- 等级：`P0`
- 领域：投喂站

描述：

- 投喂站不是简单商品列表，而是“点单 + 履约 + 记录 + 通知 + 爱心豆”的复合链路
- 一旦页面层、状态层、后端字段没有提前分清，会很容易形成新的巨石模块

可能表现：

- 页面文件继续膨胀
- 状态混乱
- 平台信息、真实金额、备注、订单状态互相缠绕
- 催单与通知逻辑不一致

缓解方案：

- 先拆 Provider / Service 再继续加功能
- 明确订单模型和状态流
- 把爱心豆逻辑和订单主逻辑分层
- 把通知当独立链路验收

最终证据：

- 下单、接单、记录、催单全链路演示
- 数据模型说明

## 3.5 联动过度设计风险

- 等级：`P1`
- 领域：首页 / 时光轴 / 爱心豆 / 记账 / 旅行 / 投喂

描述：

- 这次联动设计很多，价值很大
- 但如果没有优先级，会把项目拖进“大而全联动系统”

可能表现：

- 首页承担太多业务逻辑
- 时光轴被所有模块硬塞数据
- 联动规则彼此冲突

缓解方案：

- 只先做第一批高价值联动
- 首页只读摘要，不写业务逻辑
- 联动统一走事件或同步层

最终证据：

- 第一批联动列表实现完成
- 非必要联动没有提前侵入主流程

## 3.6 删除模块删不干净风险

- 等级：`P1`
- 领域：全局搜索 / 卡路里追踪 / 重复模块

描述：

- 删除模块最容易留下隐藏残留
- 残留可能不在入口，而在 Provider、API、菜单、常量、旧注释或后端 route

可能表现：

- 入口没了，但代码还在依赖
- 构建时没有报错，运行时才暴露缺口
- 后端还保留无意义接口

缓解方案：

- 用清理清单逐层删
- 每删一个模块都做搜索和回归检查
- 用“无残留 API / 无残留入口 / 构建通过”作为删除完成标准

最终证据：

- 删除前后清单
- 代码搜索结果
- 构建与运行验证

## 3.7 后端结构继续平铺风险

- 等级：`P1`
- 领域：`server_fixes`

描述：

- 当前后端功能已经不少
- 如果继续在平铺 route 文件上叠功能，会越来越难维护

可能表现：

- 路由归属不清
- 新人难定位逻辑
- 同类逻辑分散

缓解方案：

- 在实现过程中先按业务域给 route 分组
- 保留统一入口，但逐步引入 service 层
- 用迁移脚本和路由归属表约束新增能力

最终证据：

- 路由盘点表
- 关键域的 route / service 拆分结果

## 3.8 真机验收过晚风险

- 等级：`P0`
- 领域：全局

描述：

- 如果等所有代码做完才第一次真机看效果，返工成本会非常高

可能表现：

- 地图、天气、字体、布局、通知在电脑上看着行，真机一塌糊涂
- 发布前集中爆雷

缓解方案：

- 核心页每完成一块就抓运行态证据
- 地图和通知尽量前置真机验证
- 不到最终阶段不构建正式发布版，但要尽早验证运行态

最终证据：

- 分阶段截图 / 录屏
- 真机回归记录

## 3.9 外部依赖准备不齐风险

- 等级：`P0`
- 领域：高德 / 服务器 / 版本发布

描述：

- 高德 Key、服务器环境变量、版本发布目录、更新链路这些都不是代码本身能单独解决的

可能表现：

- 地图功能代码做完却无法跑
- 天气 / 路线接口无法请求
- 发布后更新失败

缓解方案：

- 把外部依赖单独列成前置条件文档
- 实现前先确认有哪些值必须准备
- 发布前逐项打勾

最终证据：

- 配置完成记录
- 服务器环境核对
- 更新链路验证

## 4. 风险处理顺序

后续实施时，优先处理顺序建议为：

1. 地图真机稳定性
2. UI 与参考图一致性
3. 中文文案稳定性
4. 投喂站主链路复杂度
5. 外部依赖准备
6. 删除模块残留
7. 联动范围控制
8. 后端结构平铺问题

原因很简单：

- 前 5 项如果处理晚了，会直接拖垮整轮交付

## 5. 当前阶段结论

截至 2026 年 7 月 17 日，LoveGirl 的主要风险并不是“没有想法”，而是：

- 有很多明确方向
- 但其中几条一旦处理顺序不对，会在真机阶段集中爆雷

这份风险文档的作用，就是把这些雷提前标出来。
